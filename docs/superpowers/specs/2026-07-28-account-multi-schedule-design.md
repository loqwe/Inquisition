# 账号多时间定时运行设计

## 目标

让一个日常账号在同一组活跃星期内配置 1 至 3 个运行时间，并保持现有调度优先级、失败恢复、设备协议和立即上号行为不变。

## 已确认规则

- 调度模式仍只有 `AUTO` 和 `SCHEDULED`。
- `SCHEDULED` 支持 1 至 3 个时间，时间按 `HH:mm` 升序保存。
- 同一账号的所有时间共用现有活跃星期配置。
- 相同时间不允许重复。
- 每个到点时刻只生成一个持久化运行记录。
- 同一账号仍只允许一个活动定时运行实例。
- 前一个实例未结束时，后一个到点时刻保留在数据库中，完成后按最早时间继续高优先级等待。
- 不抢占已经运行的设备，不在内存队列中重复插入账号 ID。
- 设备和 Lua 获取的任务 JSON 不增加任何调度字段。

## 数据模型

### `account_dispatch_config`

继续保存账号级调度状态：

- `dispatch_mode`：`AUTO` 或 `SCHEDULED`。
- `next_scheduled_at`：该账号所有时间中的下一个待处理时刻，也可以是已经到点但因活动实例而暂时阻塞的时刻。
- `activation_pending`：运行中修改模式或时间时延迟生效。
- `schedule_time`：兼容旧后端的首个时间摘要，不再作为新代码的唯一真源。

### `account_dispatch_time`

新增规范化时间表：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 自增主键 |
| `account_id` | BIGINT | 账号 ID |
| `schedule_time` | TIME | 每日运行时间 |
| `created_at` | DATETIME(6) | 创建时间 |
| `updated_at` | DATETIME(6) | 更新时间 |

约束：

- 唯一键 `(account_id, schedule_time)` 防止重复时间。
- 查询索引 `(account_id, schedule_time)` 支持按账号升序读取。
- 服务层限制每个账号最多 3 行。

### `account_scheduled_run`

表结构保持不变。`(account_id, scheduled_for)` 唯一键继续保证同一个到点时刻只生成一次。

## 调度算法

### 保存配置

1. 兼容读取 `scheduleTimes` 和旧 `scheduleTime`。
2. 规范化、去重并升序排列时间。
3. `SCHEDULED` 要求 1 至 3 个时间和至少一个活跃星期。
4. 在同一事务中替换 `account_dispatch_time` 行并更新账号配置。
5. 没有活动任务时，计算严格晚于当前时刻的最早有效时刻。
6. 有活动任务时写入新时间但设置 `activation_pending=1`，等当前任务关闭后重新计算。

### 每分钟扫描

1. 锁定 `next_scheduled_at <= now` 的账号配置。
2. 账号无效、过期或冻结时沿用现有跳过规则并计算未来时刻。
3. 已存在活动定时实例时不清除、不推进 `next_scheduled_at`，因此后一个时段不会丢失。
4. 到点时刻已经属于过去游戏日时跳过旧游戏日积压，计算第一个未来时刻。
5. 没有活动实例时创建唯一 `WAITING` 记录。
6. 创建成功后立即用完整时间列表计算严格晚于本次 `scheduled_for` 的下一个时刻。
7. 扫描恢复 `WAITING` 和到期 `RETRY_WAIT`，内存队列仍按账号 ID 去重。

### 多时间撞车

例如配置 `08:00 / 14:00 / 19:30`：

- 08:00 实例仍在运行时，14:00 到点后 `next_scheduled_at` 保持 14:00。
- 08:00 实例关闭后，下一次扫描创建 14:00 实例并把指针推进到 19:30。
- 若 19:30 也已经到点，则 14:00 实例结束后再创建 19:30 实例。
- 数据库最多有一个活动实例，内存队列最多有一个该账号 ID。
- 如果积压跨过游戏日 04:00，旧游戏日时段不再补跑。

## API 契约

管理员更新请求：

```json
{
  "dispatchConfig": {
    "dispatchMode": "SCHEDULED",
    "scheduleTimes": ["08:00", "14:00", "19:30"]
  }
}
```

兼容规则：

- 旧请求 `scheduleTime: "19:30"` 转为单元素列表。
- 同时传入两个字段时必须表示相同的首个时间，否则返回参数错误。
- 管理员账号列表同时返回 `scheduleTimes` 和旧 `scheduleTime`。
- `scheduleTime` 始终是升序列表首项，供旧前端显示。
- `nextScheduledAt` 继续返回账号级下一个待处理时刻。
- `AccountDTO`、`/getTask`、`/completeTask`、`/failTask`、`/sanReport` 和 `/addLog` 不变。

## 管理面板

### 编辑布局

- 保留“自动分配 / 定时运行”分段控件。
- 定时模式显示 1 至 3 个时间输入框、添加图标和每项删除图标。
- 时间区使用响应式网格，桌面最多三列，移动端单列。
- 右侧显示真实调度摘要：下次运行时间、时段数量和当前状态，不使用空白占位说明。
- 达到 3 个时间后隐藏或禁用添加按钮。
- 删除到 0 个时显示校验错误，保存按钮保持不可提交。

### 列表与任务面板

- 账号列表显示 `定时任务 / 08:00、14:00、19:30 / 正常`。
- 单个待处理或运行任务仍只显示该运行记录对应的时间。
- `AUTO` 文案保持原样。

## 迁移和回滚

- 新增 `mysql-account-multi-schedule-v2.sql`，不修改已执行的 v1 文件。
- 迁移创建时间表，并将现有 `SCHEDULED.schedule_time` 回填为一行。
- 迁移可重复执行，重复执行不会产生重复时间。
- 回滚只删除新时间表；旧 `schedule_time` 和 `next_scheduled_at` 始终保留，所以旧后端可按首个时间恢复运行。
- 新代码每次保存都同步首个时间到旧字段，保证回滚摘要有效。

## 发布顺序

1. 备份 MySQL，并执行 `mysql-account-multi-schedule-v2.sql`。
2. 部署新后端，先验证旧管理面板和旧设备协议仍可正常取任务、回报和完成任务。
3. 部署新管理面板，再验证多时间读取、保存和账号列表回显。
4. 灰度期间只允许一个后端实例参与任务分配，保持现有主备边界不变。

回滚顺序必须反向执行：先回滚管理面板，再回滚后端；确认没有新后端实例后，才可以执行 `mysql-account-multi-schedule-v2-rollback.sql`。回滚会删除第二、第三个时间，但旧 `schedule_time` 中的首个时间仍可继续运行。

## 验证门禁

- 多时间计算覆盖同日、跨日、跨星期和 04:00 游戏日边界。
- 配置覆盖旧字段兼容、排序、重复、空列表、超过 3 项和事务回滚。
- 调度覆盖活动实例阻塞不丢时段、完成后继续、跨游戏日跳过和重复扫描幂等。
- MySQL 8 覆盖首次迁移、重复迁移、回滚、再次迁移、唯一约束和 utf8mb4 排序规则。
- 前端覆盖增删、排序、校验、列表格式和响应式布局。
- 旧设备完整 JSON 树在 AUTO、MANUAL、SCHEDULED 下仍只允许 `assignmentId` 不同。
