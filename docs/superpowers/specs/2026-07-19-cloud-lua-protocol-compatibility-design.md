# 生产版 cloud.lua 协议逆向与旧客户端兼容设计

日期：2026-07-19

## 1. 目标

本工作只逆向生产版 `script.lr` 中与审判庭后端通信有关的 `cloud.lua`，还原真实请求、响应和状态转换，并据此保证现有设备在不更新客户端脚本的情况下可以继续使用新后端。

本设计不尝试恢复完整游戏自动化源码，不修改生产 `script.lr`，不重新打包客户端，也不上传或部署任何制品。

## 2. 已知事实

- 热更新接口当前可访问，并返回生产包 MD5 `de760ee66209882f057c6f1f77ed35db`。
- 当前生产 `script.lr` 包内脚本时间为 2026-07-05，包含 22 个 Lua 文件。
- 包内 Lua 使用 `0x86 4c 55 41`（`\x86LUA`）开头的懒人精灵自定义编译或加密格式。
- 本地公开 ArkLights 源码只有 12 个 Lua 文件；其中 `cloud.lua` 的上游最后修改时间是 2023-11-22，只能作为历史协议参考，不能直接打包覆盖生产版本。
- 后端当前新增了可选的 `assignmentId`、`clientVersion` 和日志身份字段，但旧客户端不会发送这些字段。

## 3. 范围

### 3.1 需要还原的客户端行为

- `heartBeat`
- `getTask`
- `addLog`
- `uploadImage`
- `completeTask`
- `failTask`
- `sanReport`
- `haltComplete`
- 服务端业务码 `200`、`201`、`409`、`500` 的客户端处理
- 客户端取到任务、启动任务、停止任务和重新取任务之间的状态转换

### 3.2 不在本次范围内

- 作战、基建、肉鸽、OCR 和森空岛客户端实现
- 完整恢复 22 个 Lua 文件的可编译源码
- 破解或绕过软件授权
- 修改、上传或替换生产脚本包
- 线上部署

## 4. 方案选择

采用“协议优先静态逆向 + 必要时运行时抓取”的组合方案。

不优先完整反编译 `\x86LUA`，因为后端兼容只依赖网络协议和状态转换。只有当静态证据无法确认关键分支时，才继续分析字节码格式或在隔离的懒人精灵环境中 hook 网络函数。

## 5. 逆向架构

### 5.1 原始制品层

保存以下只读证据：

- 原始 `script.lr`
- 包级 SHA-256 和 MD5
- ZIP 目录清单、文件大小和时间戳
- 原始编译版 `cloud.lua`

原始文件与所有派生产物分开保存，不对原始包原地修改。

### 5.2 静态分析层

按以下顺序进行：

1. 确认 `script.lr` 容器格式和 `entry.json`。
2. 记录 `cloud.lua` 文件头、长度、熵、可见字符串和重复结构。
3. 对照旧版明文 `cloud.lua` 的函数顺序、接口路径和常量，建立候选函数映射。
4. 检查懒人精灵编译器、运行时或已有工具是否能读取 `\x86LUA` 原型、常量表和指令流。
5. 如果只能恢复常量和调用关系，也以协议证据为交付目标，不强求生成可重新编译的源码。

### 5.3 动态验证层

只有静态分析存在关键空缺时才使用。动态验证在隔离环境中包装或 hook：

- `httpGet`
- `httpPost`
- `JsonEncode`
- `JsonDecode`
- `downloadFile`
- `restartPackage`
- `stop`

记录 URL、方法、请求字段、响应字段和状态转换。测试使用本地模拟后端，不向真实账号分发任务，不执行游戏自动化。

## 6. 旧客户端协议基线

| 操作 | 旧客户端最小请求 | 新字段处理 |
| --- | --- | --- |
| 心跳 | JSON：`status`、`deviceToken` | `assignmentId`、`clientVersion` 缺失时允许 |
| 获取任务 | 查询参数：`deviceToken` | 响应中的新增字段必须可忽略 |
| 日志 | 旧日志字段和设备来源 | 后端补全 `accountId`、`assignmentId` |
| 完成任务 | `deviceToken`、`imageUrl` | 缺少 `assignmentId` 时按当前设备租约处理 |
| 失败任务 | `deviceToken`、`imageUrl`、`type` | 缺少 `assignmentId` 时按当前设备租约处理 |
| 理智上报 | `san`、`maxSan`、`deviceToken` | `assignmentId` 可选 |
| 停机完成 | JSON：`status`、`deviceToken` | 新元数据可选 |

逆向结果必须逐项确认或修正该基线。

## 7. 后端兼容规则

### 7.1 客户端模式识别

- 请求携带非空 `assignmentId`：按新版严格模式验证。
- 请求未携带或携带空 `assignmentId`：按旧版兼容模式处理。
- 心跳缺少 `clientVersion`：记录为 legacy 或 unknown，但不能拒绝心跳。

### 7.2 任务提交

旧客户端完成或失败任务时，后端只能在以下条件全部成立时接受：

1. `deviceToken` 对应一个且仅一个活动任务。
2. 该任务仍在两小时硬租约内。
3. 任务当前所有者仍是该设备。
4. 设备没有处于删除、暂停或强制停机状态。

新版客户端显式提交错误 `assignmentId` 时返回 `409`，不得降级为旧版兼容模式。

### 7.3 日志

- 旧日志缺少任务编号时，后端根据 `from/deviceToken` 查询当前活动任务并补全身份。
- 没有活动任务、租约已过期或设备不匹配时，日志可以留作审计，但不能刷新账号的九小时有效日志锚点。
- 只有被分类为有效游戏日志且通过当前任务验证的日志，才能更新账号运行时状态。

### 7.4 心跳和停机

- 旧心跳必须正常刷新设备在线时间和状态。
- 任务被回收或设备被移除后，心跳返回停机业务码。
- 在旧设备完成停机确认前，不给该设备分配新任务，避免旧进程结果污染后续任务。
- `haltComplete` 必须幂等。

### 7.5 响应兼容

- 保留旧响应字段和旧业务码语义。
- 新字段只能追加，不能重命名或改变旧字段类型。
- 旧客户端不认识 `assignmentId` 时应能忽略该字段并继续执行。

## 8. 无客户端更新时的固有限制

旧客户端不回传任务编号，因此服务端无法在所有极端竞态中数学上证明某次提交属于哪一代任务。服务端通过单活动租约、租约过期校验、停机握手和重新分配门禁降低风险，但严格的跨代提交识别只有客户端携带 `assignmentId` 才能完全实现。

因此设计目标是：旧客户端保持可用且常规故障恢复安全；新版字段作为未来增强，不作为当前部署前置条件。

## 9. 错误处理

- 下载或解包失败：保留错误、URL、HTTP 状态和已下载字节数，不覆盖原始证据。
- 字节码无法反编译：转为常量表、调用关系和动态网络抓取，不猜测源码。
- 完成或失败上报无法归属当前有效任务：返回 `409`，要求设备停止当前任务并重新获取。
- 理智上报找不到当前任务：返回 `404`；日志仍可留作审计，但不得更新账号运行时锚点。
- 重复完成、失败或停机请求：保持幂等，不重复修改队列或发送通知。
- 逆向证据与旧源码冲突：以生产运行行为、抓包和生产包为准。

## 10. 测试设计

### 10.1 协议契约测试

使用旧客户端最小请求覆盖：

- 不带新增字段的心跳返回成功。
- 不带 `assignmentId` 的完成和失败上报能够处理当前有效任务。
- 不带新增身份字段的日志可以由后端补全。
- 不带 `assignmentId` 的理智上报可以更新当前账号。
- 不带新增字段的停机确认可以重复调用。

### 10.2 安全回归测试

- 显式错误 `assignmentId` 返回 `409`。
- 已过期租约的旧式提交被拒绝。
- 其他设备的提交被拒绝。
- 没有活动任务的旧日志不能刷新九小时锚点。
- 设备停机完成前不能获得新任务。
- 新增响应字段不改变旧字段序列化结果。

### 10.3 逆向验证

- 静态提取的接口和字段与旧源码逐项比较。
- 如果进行动态抓取，同一操作至少重复两次，确认字段和状态码稳定。
- 对所有不确定结论标记证据等级，不把推测写成事实。

## 11. 交付物

- `cloud.lua` 协议和状态机说明。
- 生产包证据清单与哈希。
- 新旧字段兼容矩阵。
- 逆向笔记和派生工具，原始制品不入修改流程。
- 后端兼容缺口及对应自动化测试。
- 未解决项、残余风险和后续客户端升级建议。

## 12. 完成标准

满足以下条件后，本项工作才算完成：

1. 八个目标接口的请求、响应和关键状态转换均有生产证据或明确的不确定标记。
2. 旧客户端最小请求契约全部通过自动化测试。
3. 新版显式任务编号校验仍然有效。
4. 两小时租约、掉线回收、停机门禁和九小时日志锚点不依赖客户端升级。
5. 没有修改、打包、上传或部署生产脚本。
