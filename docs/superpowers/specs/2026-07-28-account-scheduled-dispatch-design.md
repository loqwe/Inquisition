# 账号自动分配与定时运行设计

## 目标

为日常账号增加 `自动分配 / 定时运行` 两种调度方式。定时账号在配置时间到达后执行与自动账号完全相同的完整日常任务，并以“立即上号”同级的高优先级持续等待设备；现有自动账号的分配、失败恢复和设备兼容行为保持不变。

本设计的首要约束是旧设备协议零变化。调度方式只属于后端控制面，不属于下发给 Lua 设备的任务协议。

## 已确认规则

- 每个账号只有一种调度方式：`AUTO` 或 `SCHEDULED`。
- 旧账号和未创建定时配置的账号均按 `AUTO` 处理。
- 第一版每个定时账号配置一个 Asia/Shanghai 墙上时间，例如 `19:30`。
- 定时任务只在账号现有“活跃时间”中勾选的星期执行。
- 到点后执行完整日常任务，不是仅登录任务。
- 到点没有空闲设备时持续高优先级等待，不因过点或跨 04:00 自动失效。
- 同一账号最多保留一个未完成的定时运行实例。旧实例未完成期间不生成新实例，也不补建错过日期的实例。
- 旧实例完成后，从完成时刻之后的下一个有效时间继续，不回补中间错过的日期。
- 优先级为：`26点加急 > 定时任务 = 立即上号 > 普通自动分配`。
- 同级任务按进入高优先队列的时间先后分配。
- 高优先任务不抢占设备已经接收的任务。
- 切换调度方式不打断正在运行的任务，变更在当前运行实例结束后生效。

## 非目标

- 不修改 Lua 脚本或要求设备升级。
- 不增加新的设备端 `taskType`。
- 不把定时任务转换为 `LOGIN_ONLY`。
- 不实现一个账号一天多个定时时间。
- 不实现主动—主动多后端或完全数据库化的分布式任务队列。
- 不改变 14 点和 26 点任务本身的业务目的。

## 现有系统约束

当前等待队列是 `DynamicInfo.waitUserList` 中的账号 ID 列表。生产代码中存在多条直接入队路径，包括：

- 启动时载入全部有效日常账号；
- 从 `data.json` 恢复旧等待列表；
- 理智达到阈值后重新入队；
- 管理员、用户和专业用户“立即上号”；
- 任务失败、设备掉线、两小时超时后的回收；
- 冷却到期和重启恢复；
- 14 点补登、26 点加急及加急手动重试；
- 强制刷新全部任务和每分钟队列去重。

因此，仅在启动查询中排除定时账号不能实现隔离。任何一条恢复路径都可能把定时账号重新放回普通自动队列。实现必须收口全部队列写操作，并保留每次运行的调度来源。

## 方案选择

采用“统一入队服务并保留现有内存队列”的方案：

- 保留 `waitUserList` 作为账号级等待顺序，降低对现有任务看板、心跳和状态查询的影响。
- 新增 `DispatchQueueService`，成为等待队列唯一写入口。
- 用持久化的加急任务和定时运行实例，以及进程内的一次性手动意图，解析账号当前有效来源。
- 在创建任务租约时把最终调度来源写入 MySQL，后续失败、离线和超时恢复按原来源处理。

不采用散落条件判断，因为它无法覆盖所有回队入口；也不在本期把全部自动队列迁移到 MySQL，因为这会扩大现有自动账号的回归范围。

## 设备协议硬约束

定时任务必须走现有普通完整任务分支：

```text
taskMode = NORMAL
taskType = daily
config = 账号原有完整日常配置，经现有 DailyPlan 编译
```

以下后端字段不得出现在设备响应 JSON 中：

```text
dispatchMode
scheduleTime
nextScheduledAt
dispatchSource
scheduledRunId
priority
scheduledFor
```

为避免 `AccountDTO extends AccountEntity` 自动泄露新增字段，定时配置不加入 `AccountEntity`。它保存在独立的 `account_dispatch_config` 表，并只拼装到管理员账号列表 VO。`TaskServiceImpl.buildTaskAccountDTO` 继续只从原有 `AccountEntity` 生成设备 DTO。

实现验收必须保存一份普通 `AUTO` 账号的设备 JSON 基线，并分别对 `AUTO`、`SCHEDULED`、`MANUAL` 三种完整日常分配做结构化 JSON 比较：除每次本来就会变化的 `assignmentId` 外，字段集合、字段类型、`taskType` 和 `config` 必须完全一致。禁止只检查几个字段或只确认 HTTP 200。

现有 26 点加急仍可使用既有 `LOGIN_ONLY` 临时负载；这属于已经存在的独立功能，不得被定时任务复用。

## 数据模型

### 账号调度配置

新增表 `account_dispatch_config`，不修改设备使用的账号实体。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `account_id` | BIGINT PK | 对应账号 ID |
| `dispatch_mode` | VARCHAR(16) | `AUTO` 或 `SCHEDULED`，默认 `AUTO` |
| `schedule_time` | TIME | 定时模式的墙上时间 |
| `next_scheduled_at` | DATETIME(6) | 下一次应生成实例的时间；有未完成实例时为 NULL |
| `activation_pending` | TINYINT | 有运行中租约时配置等待生效，默认 0 |
| `created_at` | DATETIME(6) | 创建时间 |
| `updated_at` | DATETIME(6) | 更新时间 |

不存在配置行时等价于 `AUTO`。这样迁移后无需一次性回填全部账号，也不会改变现有账号序列化结果。

`next_scheduled_at` 由后端计算并持久化，作用如下：

- 服务短暂停机但仍处于同一游戏日时，可补建已经到点的唯一实例；
- 未完成实例跨日时不会生成第二个实例；
- 旧实例完成后从未来时间继续，不回补错过日期；
- 管理端可直接展示真实下一次运行时间。

若服务恢复时 `next_scheduled_at` 已属于早于当前游戏日的旧游戏日，说明该触发点从未生成实例；服务不补建陈旧任务，而是直接推进到严格晚于当前时刻的下一个有效时间。已经生成的 WAITING、RUNNING、RETRY_WAIT 实例不受这条规则影响，仍可跨任意数量的游戏日持续保留。

### 定时运行实例

新增表 `account_scheduled_run`。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK AUTO_INCREMENT | 定时实例 ID |
| `account_id` | BIGINT | 账号 ID |
| `scheduled_for` | DATETIME(6) | 原计划触发时间 |
| `game_day` | DATE | 按现有 04:00 游戏日规则计算 |
| `status` | VARCHAR(24) | 生命周期状态 |
| `attempt_count` | INT | 已开始分配的次数 |
| `next_retry_at` | DATETIME(6) | 现有递增冷却的结束时间 |
| `last_error` | VARCHAR(255) | 最近失败原因，禁止写密码或 Token |
| `created_at` | DATETIME(6) | 创建时间 |
| `updated_at` | DATETIME(6) | 更新时间 |
| `finished_at` | DATETIME(6) | 终态时间 |

约束和索引：

- 唯一键 `(account_id, scheduled_for)` 防止同一触发点重复创建。
- 调度索引 `(status, next_retry_at, scheduled_for)` 支持到期恢复。
- 服务在事务内锁定账号的调度配置行，先检查是否已有活动实例，再创建新实例并把 `next_scheduled_at` 置空。
- 当前系统仍为单后端调度；本约束不宣称支持两台后端主动—主动并发领取。

### 任务租约来源

在 `task_assignment` 和 `task_assignment_history` 增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `dispatch_source` | VARCHAR(24) | `AUTO`、`MANUAL`、`SCHEDULED` 或 `URGENT_26` |
| `scheduled_run_id` | BIGINT NULL | 定时实例 ID，仅定时来源使用 |

这些字段只用于后端恢复和审计，不进入设备 DTO。

## 生命周期

定时实例状态如下：

```text
WAITING -> RUNNING -> SUCCEEDED
   |          |
   |          +-> RETRY_WAIT -> WAITING
   +--------------> RETRY_WAIT -> WAITING

WAITING / RUNNING / RETRY_WAIT -> CANCELLED
WAITING / RUNNING / RETRY_WAIT -> FAILED（仅不可恢复错误）
```

- `WAITING`：已到点且可分配，处于高优先等待。
- `RUNNING`：设备已取得完整日常任务。
- `RETRY_WAIT`：失败、掉线或超时后处于现有递增冷却。
- `SUCCEEDED`：设备正常完成完整日常任务。
- `CANCELLED`：管理员切回自动模式、删除账号或显式取消。RUNNING 只在当前租约关闭后才能进入 CANCELLED，不会因此抢占设备。
- `FAILED`：账号配置损坏等不可恢复错误。普通设备失败不进入终态，而是继续递增重试。

实例进入终态后，如果账号仍为有效 `SCHEDULED` 模式，服务以终态时间为基准计算严格晚于当前时刻的下一个启用星期和时间，并写入 `next_scheduled_at`。中间已经错过的日期不补建。

## 时间和星期语义

- 所有定时计算使用 `Asia/Shanghai`，不依赖宿主机默认时区。
- `schedule_time` 使用 24 小时墙上时间，例如 `19:30`。
- 活跃星期沿用账号现有 `active` JSON。
- 星期按实际墙上日期判断。若以后允许 `02:30`，则星期指日历当天；其 `game_day` 仍按现有 04:00 规则归属前一个游戏日。
- 定时模式至少要启用一个活跃星期，否则保存失败。
- 活跃星期只用于计算并创建定时实例。实例创建后，WAITING、RUNNING、RETRY_WAIT 的领取和恢复不得再次按当前星期或 04:00 校验；跨 04:00 或进入未启用星期不得移除、降级或转换该实例。

## 统一队列与优先级

`DispatchQueueService` 是 `waitUserList` 的唯一写入口，负责：

- 入队、移除、重新排序和去重；
- 校验账号删除、冻结、到期、调度方式和任务类型；
- 解析账号当前有效的一个或多个调度意图；
- 计算当前最高有效优先级；
- 在任务领取时返回调度来源和对应实例 ID；
- 根据任务租约来源执行失败、离线和超时后的恢复。

优先级常量：

```text
URGENT_26 = 300
SCHEDULED = 200
MANUAL    = 200
AUTO      = 100
```

同一账号仍只在 `waitUserList` 中出现一次。如果同一账号同时存在 26 点加急和未完成定时实例，队列按 `URGENT_26` 分配；加急登录结束后，未完成的定时实例仍存在，账号恢复为 `SCHEDULED` 高优先级并执行完整日常。

不同账号同级时按该意图首次变为可分配的时间排序。普通 `AUTO` 账号之间继续保持现有队列顺序，不因新增服务重新排序。

### 入队策略矩阵

| 入口 | AUTO 账号 | SCHEDULED 账号 |
| --- | --- | --- |
| 启动普通加载 | 加入普通队列 | 不加入 |
| `data.json` 恢复 | 校验后恢复为 AUTO | 丢弃陈旧普通项；从 MySQL 实例恢复 |
| 理智达到阈值 | 加入普通队列 | 只更新理智，不入队 |
| 强制刷新全部任务 | 重建普通层 | 保留活动定时/加急，不加入普通层 |
| 14 点补登 | 按现有规则提升 | 不参与普通补登 |
| 26 点最终补登 | 可创建最高优先加急 | 同样可创建最高优先加急 |
| 立即上号 | 创建 MANUAL 同级高优先意图 | 无活动定时实例时创建 MANUAL；有活动实例时复用原 SCHEDULED 实例 |
| 定时扫描到点 | 无操作 | 创建或恢复唯一 SCHEDULED 实例 |

“立即上号”是一次性运行，不修改固定时间。若该账号已有活动定时实例，立即上号不创建 MANUAL 意图：WAITING 保持原实例，RETRY_WAIT 清除本次冷却并提前恢复为 WAITING；后续租约仍写入 `dispatch_source=SCHEDULED` 和原 `scheduled_run_id`，完成及失败继续驱动该定时实例。若尚未到定时时间，则创建独立 MANUAL 运行，固定时间仍按原计划生效。

## 任务领取与恢复

设备调用现有获取任务接口时，流程保持原有授权、心跳、设备暂停、作用域、B服限制、重复分配和冷却检查。AUTO 和 MANUAL 继续遵守现有活跃时间检查；已经生成的 SCHEDULED 实例不再检查当前星期，避免跨日等待后永久无法领取。变化只发生在候选账号来源解析和租约记录：

1. 选择当前最高有效意图。
2. 创建任务租约，写入 `dispatch_source` 和可选 `scheduled_run_id`。
3. 对 SCHEDULED 实例原子更新为 `RUNNING` 并增加尝试次数。
4. 继续调用现有 `buildTaskAccountDTO`，不把来源信息加入响应。
5. 租约成功后再从等待队列移除账号。

恢复规则：

- `AUTO` 失败、掉线、超时：维持现有普通重试行为。
- `MANUAL` 失败、掉线、超时：维持一次性高优先来源，直到本次运行完成或取消。
- `SCHEDULED` 失败、掉线、超时：更新同一个定时实例并按现有递增冷却恢复为高优先，不转换成 AUTO。
- `URGENT_26` 失败、掉线、超时：维持现有加急重试行为。
- 后端重启：活动租约从 MySQL 恢复；WAITING/RETRY_WAIT 定时实例从 MySQL 恢复；`data.json` 只可恢复通过当前调度策略校验的普通项。

任务来源在租约创建后固定。账号在任务运行中切换模式时不改变当前租约，配置行写入目标配置并设置 `activation_pending=1`、`next_scheduled_at=NULL`。当前租约关闭时，后端先判断配置是否待生效：若待生效，则不按旧来源继续回队，原子应用目标配置，并以关闭时刻为基准计算新模式的后续状态；未变更模式时才按原来源执行既有重试。后端重启时也必须修复“待生效但已无活动租约”的配置。

## 模式切换和账号状态变化

### AUTO 切换为 SCHEDULED

- 校验时间和至少一个活跃星期。
- 移除尚未分配的普通 AUTO 意图。
- 不打断当前运行任务。
- 没有活动租约时，从保存时刻之后计算下一个未来有效时间，不立即回补当天已经错过的时间。
- 存在活动租约时设置 `activation_pending=1` 且不写入下一次时间；租约关闭后再以关闭时刻计算严格未来的首次触发时间。

### SCHEDULED 切换为 AUTO

- 清空 `next_scheduled_at`。
- 尚未运行的 WAITING/RETRY_WAIT 定时实例标记为 `CANCELLED`。
- 当前 RUNNING 实例不被打断并将配置标记为待生效；租约成功完成时实例进入 SUCCEEDED，失败、离线或超时关闭时实例进入 `CANCELLED` 并记录 `MODE_CHANGED`，随后启用 AUTO，不再按 SCHEDULED 来源重试。
- 账号按现有自动规则重新进入普通生命周期，不额外伪造理智阈值。

### 修改时间或活跃星期

- 没有活动实例时，从保存时刻之后重算 `next_scheduled_at`。
- 已有活动实例时不修改本次实例；实例结束后按新配置计算下一次时间。

### 冻结、删除和到期

- 冻结时不创建新定时实例；尚未运行的定时实例取消，避免解冻后执行陈旧日常。
- 已经运行的任务不因保存配置直接中断，管理员可使用现有结束任务操作。
- 删除或到期账号取消等待中的定时实例并停止计算下一次时间。
- 解冻、恢复或续期后，如果仍为 SCHEDULED，则从恢复时刻之后计算下一个未来有效时间。

## 26 点加急交互

26 点最终补登继续覆盖所有有效日常账号，包括 SCHEDULED 账号。

- 定时实例尚在 WAITING/RETRY_WAIT：账号以 `URGENT_26` 最高优先级先执行既有 LOGIN_ONLY；登录成功后定时实例继续以 SCHEDULED 高优先等待完整日常。
- 定时完整日常已经 RUNNING：不抢占；其登录成功日志可按现有规则完成当日加急标记，完整日常继续运行。
- 加急失败：按加急来源重试，不覆盖定时实例的状态和尝试次数。

这样既保留 26 点“必须登录”的兜底，也不把定时完整日常误判为已经完成。

## 调度任务和监控

在现有脚本任务监控中新增：

```text
key: account-scheduled-dispatch
name: 账号定时调度
cron: 0 */1 * * * *
schedule: 每1分钟
timezone: Asia/Shanghai
```

每次扫描：

1. 查找 `SCHEDULED` 且 `next_scheduled_at <= now` 的有效账号。
2. 在事务中锁定配置行并检查活动实例、活动租约和待生效状态。
3. 触发点仍属于当前游戏日时创建唯一实例、清空下一次时间并通过统一队列入队。
4. 触发点早于当前游戏日且从未生成实例时不补建，直接推进到下一个未来有效时间。
5. 恢复已经结束冷却的 RETRY_WAIT 实例；已生成实例不重新检查星期或游戏日。
6. 记录扫描数量、创建数量、推进数量、跳过原因、耗时和异常。

该任务自动出现在现有“脚本任务”页面，接受相同的迟到、连续失败和运行中检测。日志不得包含账号密码、设备 Token 或森空岛凭据。

## 管理端设计

### 编辑账号

位置：编辑账号对话框的“其他”页签，在现有“活跃时间”上方。

- 使用分段控件显示 `自动分配 / 定时运行`。
- 选择定时运行后显示时间输入控件。
- 星期继续使用现有活跃时间复选框，不新增第二套星期选择。
- 定时模式缺少时间或未选择任何星期时禁止保存并给出字段级错误。
- 保存失败时保留对话框内容，不显示成功状态。

调度配置作为管理员更新请求中的独立 `dispatchConfig` 对象处理，不写入设备使用的 AccountDTO。旧管理端不发送该对象时，后端保持原配置不变。

### 账号列表

不增加单独信息行，复用现有“任务类型”位置：

```text
AUTO:       任务类型: 日常任务
SCHEDULED:  任务类型: 定时任务 / 19:30 / 正常
```

定时状态显示规则：

- `未运行`：从未成功运行且当前无活动实例。
- `等待中`：WAITING。
- `运行中`：RUNNING。
- `重试中`：RETRY_WAIT。
- `正常`：最近实例 SUCCEEDED 且当前无活动实例。
- `失败`：最近实例为不可恢复 FAILED。

账号冻结、删除和到期仍由现有独立徽标表示，不混入定时运行结果。

### 任务管理

保留现有三个页签和 26 点加急置顶规则。定时任务属于完整日常任务：

- 在待处理或进行中项目上增加简短“定时”来源标识。
- 不新增第四个页签。
- 定时任务与立即上号同级，但始终位于普通 AUTO 任务之前。
- 26 点加急存在时仍显示在所有定时和普通任务之上。

## API 和兼容

- 现有设备接口路径、请求参数、响应代码和旧客户端缺少 `assignmentId` 的兼容逻辑不变。
- 管理员账号查询 VO 增加 `dispatchMode`、`scheduleTime`、`nextScheduledAt` 和 `scheduleStatus`。
- 管理员账号更新请求可选增加 `dispatchConfig`；未提供表示“不修改”，不能默认为 AUTO 覆盖旧值。
- 服务端对白名单字段、枚举、时间格式、账号状态和活跃星期做校验。
- 后端调度配置和账号活跃星期更新放在同一事务中，避免时间已保存但星期未保存的部分成功。
- 前端不得根据 UI 隐藏作为权限边界；更新仍走现有管理员鉴权。

## 迁移与发布

新增独立 MySQL 8 迁移和对应回滚脚本：

1. 创建 `account_dispatch_config` 和 `account_scheduled_run`。
2. 为活动实例查询、到期扫描和账号历史建立索引。
3. 给当前任务表和历史表增加来源字段，默认 `AUTO`，保证旧行可读。
4. 不回填账号配置表；无记录即 AUTO。

推荐发布顺序：

1. 备份数据库和现有镜像。
2. 执行幂等迁移并验证重复执行。
3. 发布默认关闭 `inquisition.accountSchedule.enabled=false` 的后端。
4. 验证 AUTO 设备 JSON 快照与旧版本一致。
5. 开启功能并只配置一个测试账号做灰度。
6. 验证定时触发、失败恢复、跨重启和管理端显示。
7. 发布前端。

紧急回滚时先关闭功能开关，使扫描器停止创建新实例；现有 AUTO 分配继续工作。随后回滚前端和后端镜像。数据库表和新增列先保留，确认没有新版本实例后再执行回滚 SQL，避免丢失审计状态。

## 测试与验收

### 后端行为测试

- 旧账号缺少配置行时按 AUTO 运行。
- 到点前不入队，到点后只创建一个实例。
- 只在启用星期运行，使用 Asia/Shanghai。
- 服务在同一游戏日内越过触发时间后只补建一个实例。
- 服务恢复时触发点已属于旧游戏日则不补建，直接推进到未来时间。
- 无设备时跨 04:00 保持同一实例，不生成或回补其他日期。
- 已生成实例跨 04:00 或进入未启用星期后仍可领取和恢复。
- 旧实例完成后只计算下一个未来时间。
- 定时和立即上号同级 FIFO，均低于 26 点且高于 AUTO。
- 高优先任务不打断已有任务。
- 理智刷新、14点扫描、强制刷新和 `data.json` 恢复不会把定时账号作为 AUTO 入队。
- 失败、离线、两小时超时和重启恢复保留 `SCHEDULED` 来源及同一个实例 ID。
- 活动定时实例上的“立即上号”不创建 MANUAL 来源，并继续使用原定时实例 ID。
- 有活动租约时切换模式先标记待生效，租约关闭前不生成新模式任务。
- 模式切换、时间修改、冻结、删除、到期和恢复符合状态转换规则。
- 定时实例与 26 点加急同时存在时先执行加急，随后恢复完整定时任务。
- 所有原 AUTO 队列顺序和现有测试保持通过。

### 设备协议测试

- 固定同一个账号配置，分别构造 AUTO、SCHEDULED 和 MANUAL 的 NORMAL 租约。
- 对 `buildTaskAccountDTO` 序列化结果做完整 JSON 树比较，排除动态 `assignmentId` 后必须相等。
- 明确断言 `taskType=daily`，日常计划、战斗、基建、信用、招募等配置均与原账号一致。
- 明确断言响应不包含任何调度配置、来源、优先级或定时实例字段。
- 保留现有普通任务不暴露 LOGIN_ONLY 专用字段的回归测试。
- 使用旧 Lua HTTP 请求样本验证获取、日志、完成和失败接口，无需新增参数。

### 数据库测试

- 迁移首次执行、重复执行、回滚和再次迁移。
- 同一 `(account_id, scheduled_for)` 不能重复。
- 配置行锁和事务回滚不会留下“已清空 next time 但未创建实例”的半状态。
- 任务关闭历史完整保留来源和定时实例 ID。

### 前端测试

- AUTO 模式不显示时间输入，账号列表仍为“任务类型: 日常任务”。
- SCHEDULED 模式显示时间并校验活跃星期。
- 列表严格显示“定时任务 / 19:30 / 状态”，不增加额外行。
- 状态映射覆盖未运行、等待、运行、重试、正常和失败。
- 桌面和手机宽度下文本不溢出，编辑对话框无控件重叠。

### 发布验收

- 后端全量测试和 `bootJar` 通过。
- 前端测试、类型检查和生产构建通过。
- 使用一个测试账号验证真实到点下发完整日常。
- 比较发布前后真实设备响应 JSON，确认旧协议字段集合不变。
- 模拟无设备、失败、离线、后端重启和跨 04:00，确认始终是同一实例。

## 完成标准

只有同时满足以下条件才可视为功能完成：

- 定时账号按指定星期和时间触发完整日常任务；
- 无设备时保持同级高优先且跨日不重复；
- 所有恢复路径保留原任务来源；
- AUTO 账号行为回归通过；
- 旧设备收到的普通完整任务 JSON 与发布前一致；
- 数据迁移、监控、前端显示、灰度和回滚均有真实验证证据。
